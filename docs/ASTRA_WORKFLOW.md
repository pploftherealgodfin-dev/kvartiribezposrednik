## Един източник на истина

Всяка сесия започва с актуалния `project_plan.md`, текущия commit, отворените PR и резултата от последния backend преглед. Astra е работен партньор за анализ и review; не приемаме, че има достъп до ресурс, докато действителна заявка не го докаже. Име на модел не заменя човешки контрол или изпълнени тестове.

Не използвай разговорната памет като доказателство, че функционалност работи. Разделяй „видяно в код“, „проверено в база“, „тествано през API“, „публикувано“ и „предложено“.

## Формат на всяка задача

- Проблем и конкретен сценарий, който го възпроизвежда.
- Обхват: засегнати файлове, таблици, политики и API.
- Критерии за приемане: наблюдаеми резултати, включително отказан неправомерен достъп.
- План за rollback при миграция/данни.
- Един PR с описание, проверки и действителен deployment статус.

Не смесвай почистване на демо данни с пренаписване на auth и преместване на backend в един голям PR.

## Prompt за security review

> Прегледай конкретния PR и актуалните Supabase grants, RLS, functions, triggers и Storage policies. Провери достъп като гост, собственик А, собственик Б и модератор чрез директни API заявки. ## Prompt за седмичен преглед

> Сравни плана с реалните merges, deployments и модераторски показатели. Покажи завършени задачи с доказателства, блокирани задачи с точна причина, три следващи приоритета и необходимия човешки ресурс. Не променяй числата с оценки и не третирай липсата на доклади като липса на измами.

## Условия преди публичен пилот

Backend достъпът е правилен; демо данните са изчистени; разрешенията са тествани; има човек за сигнали; възстановяване от backup е проверено; текстовете за проверки съответстват на действителния процес. Правила, поверителност и обработката на документи минават през професионален правен преглед.

Ако някое условие липсва, Astra продължава по блокера и отчита липсата. Не попълва пропуските с уверено описание на несъществуваща защита.
